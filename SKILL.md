# Automate UGC Product Videos

Run a continuous two-stage workflow: prepare and validate every prompt first, then immediately execute the validated initial video batch. A user request to produce videos authorizes that initial batch; do not pause for a second whole-batch approval. Keep the batch integrity digest as a tamper check, not as a user-approval token. A new paid replacement after a definite failure remains a separate action and still requires explicit user intent. Every requested variant must remain a creator-led UGC video; never substitute a product commercial, catalog montage, faceless showcase, or voiceover-only video.

## Required runtime

1. Call `load_workspace_dependencies` and use its Node.js, Python, and Node package paths. Do not guess global runtimes or install packages.
2. Before preparing a real batch, ensure `<workspace>/.env` exists. If it is missing, create it automatically from [assets/env.example](assets/env.example), stop, and tell the user exactly where it was created and to replace `sk-replace-locally` with `VINTED_API_KEY=sk-...`. Additional workers use `VINTED_API_KEY_2`, `VINTED_API_KEY_3`, and so on; numbering may skip values and is sorted numerically. Validate every configured key for placeholders, format errors, and duplicates before any upload or paid request. Never ask the user to paste keys into chat and never print or persist their values. Continue only on a later turn after the user confirms the local file was updated.
3. Read [references/input-schema.md](references/input-schema.md) before ingesting a workbook and [references/prompt-contract.md](references/prompt-contract.md) before authoring prompts.
4. Read [references/vinted-api.md](references/vinted-api.md) before execution and [references/operations.md](references/operations.md) for resume, retry, or failure handling.
5. If the user needs a blank input workbook, provide [assets/product-video-input-template.xlsx](assets/product-video-input-template.xlsx).

## Reference-image gate

Before prompt authoring and execution, read [references/reference-image-review.md](references/reference-image-review.md), visually inspect every reference image, and save the hash-bound image-review sidecar. SD2.5 input references must contain no faces under this workflow; generated creators still appear on camera. Face-bearing style screenshots are for local visual interpretation only. Unchecked, uncertain, face-containing, changed or unavailable references prevent only their own tasks from uploading or generating; report them and continue other tasks.

## Stage 1: prepare and review

When creating or completing a workbook, store product images as relative local paths or a JSON array of relative paths in the image cell; do not embed generated images. Enforce at most 9 images per product. For a synthetic test product, create at least 3 visually consistent white-background product angles.

1. Run `prepare` without a prompt file. Pass the absolute input workbook, Node packages, Python runtime, and env file. It produces `batch.draft.json` and prints a compact JSON summary.
2. Use the draft's products, claim IDs, task slots, and fact-filtered diversity dimensions to author one task object per slot. Except for the exact spoken dialogue, write every scene instruction, label, constraint, and production direction in Chinese. Read and copy both the mandatory Chinese user template and the Chinese production lock from [references/prompt-contract.md](references/prompt-contract.md) verbatim into every `prompt_en`; English production prose is forbidden. Every prompt must first define a specific U.S. creator and a fact-related, well-maintained modern home with a few concrete everyday background items, natural window light, and realistic close phone-camera texture, then provide the exact five time blocks 0—5, 5—11, 11—18, 18—25, and 25—30 seconds. Each time block must include a concrete camera/action plan and its own exact English spoken line; `dialogue_en` is the ordered concatenation of those five lines. Require `真人出镜：` in Hook and CTA and `创作者实操：` in Pain, Solution, and Proof. Keep the same creator as the primary human subject, with their face visible in every shot, including the first and last frame, and occupying a meaningful part of the composition for at least 70% of runtime. Every middle stage must explicitly keep the creator's face or upper body visible in-frame. Limit the video to at most two natural jump cuts. White-background references define product identity only and must not become the generated setting. Explicitly prohibit product-only or prop-only shots, product beauty-shot sequences, commercial before/after montages, voiceover-only montages, and fact-unsupported demonstration props. Ordinary background furnishings that do not participate in demonstrations or imply product claims are allowed; avoid damaged cabinets, decay, empty showrooms, and staged luxury. Save a UTF-8 JSON batch with `schema_version`, the draft's `batch_id`, and `tasks`. Each task contains `task_key`, `creative_signature`, `claim_ids`, `creative_plan`, `fact_bindings`, `dialogue_en`, and `prompt_en`. Use the complete object and array schemas in [references/prompt-contract.md](references/prompt-contract.md); `creative_plan` quotes actual instruction evidence for all six assigned dimensions and `fact_bindings` quotes the supplied sources for claims, actions, and demonstration props.

3. Immediately after authoring the complete prompt batch, run `validate-prompts` for structural checks. Without `--review`, inspect `structure_ok` and fix structural errors; overall `ok` remains false until independent semantic review is supplied. Give a separate subagent the draft, full prompt batch, and prompt contract to review every task for factual support, visible creator continuity, actual creative differences, natural English, and home visual quality (the `home_visual_quality` review check). The author must not manufacture an independent review by filling approval flags. If a separate agent is unavailable, an independent human reviewer must provide the review. Follow the sidecar schema in [references/prompt-contract.md](references/prompt-contract.md), then rerun `validate-prompts --review <prompt-review.json>`. It saves `prompt-validation.json` plus an immutable, content-addressed report used by the manifest. Inspect every returned error; revise the affected prompt and rerun until the report has `ok: true` and zero errors. The structural validator checks every task independently, regardless of product video count, including the exact Chinese user template, exact Chinese production lock, specific creator profile, product-and-scene description, all five timed camera/action blocks, per-stage English lines and their exact concatenation into `dialogue_en`, absence of English instruction prose outside those lines, all five UGC stage anchors, eye behavior, technical locks, fact-source quotation bindings, and creative-plan evidence. These checks do not establish semantic truth: the separately recorded review must check complete claim/action/prop coverage and actual differences. Review records bind all task, slot, and product inputs by hash; a changed input invalidates review.
4. Only after both structural validation and independent semantic review pass, rerun `prepare` with `--draft`, `--prompts`, `--review`, and `--image-review`. It validates again, records the successful report in the manifest, initializes SQLite, creates a backup, writes the product progress columns and `AI视频任务` sheet, and returns the immutable integrity digest. Fresh paid submissions reject manifests without both successful structural validation and independent semantic review.
5. Summarize product count, task count, invalid rows, per-product reference-image issues and tasks that will be skipped, validation report, integrity digest, and representative prompts as a progress update. Continue directly to `execute` without asking for whole-batch approval.

## Stage 2: execute

1. Run `execute` immediately after the validated manifest is ready; the initial batch does not use `--approve`. The internal integrity digest and complete executable request must match the frozen manifest and SQLite. New paid tasks require the current structural and independent semantic review; existing paid jobs and uncertain submissions can recover under their original integrity digest without reauthoring old prompts. Once a task has been initialized, changed prompts, images, or request settings require a fresh draft/batch and fresh validation. Never edit the old manifest or delete its database to bypass this check.
2. Keep the command running while it emits per-task progress and a 30-second heartbeat. A per-state-database execution lock prevents concurrent mutation of the same batch. Create one worker for each valid API key and feed unsubmitted tasks from a shared FIFO queue. A worker owns exactly one full lifecycle—reference check, upload, create, poll, download, MP4 validation, and client shutdown—and may claim another task only after every request and socket from the prior task has closed. One key therefore runs strictly serially; multiple keys run at most one lifecycle each in parallel. Every `POST /v1/videos` attempt, including 409-without-ID, 429, 5xx and network retries, must start at least 31 seconds after that same key's preceding create attempt. Persist the per-key cadence before sending so restarts preserve the remaining delay. `POST /v1/files`, polling, signed-URL retrieval, and downloads do not add another cadence delay, but remain inside the owning worker's lifecycle.

3. Bind a task to a batch-scoped one-way credential identifier and a safe display slot such as `key-2`; never write a raw key to SQLite, manifests, workbooks, JSON, or logs. Existing `job_id` and `submission_unknown` tasks stay pinned to their original key, frozen image IDs, request body, and idempotency key. If that key is absent, block only the pinned task. Bind legacy submitted tasks without a credential to the primary key; leave fresh tasks unbound for the next idle healthy worker. A definite 401/402/403 disables only its key. If the create was certainly not accepted, clear the old image and credential binding and let another healthy worker claim that task; accepted or uncertain work stays pinned. A definite 429 keeps the task on the same worker, records `Retry-After`, and retries only after both cooldown and that key's 31-second cadence. Catalog incompatibility and batch-integrity invalidation stop all new submissions.

4. Accepted jobs are polled every four seconds until the provider returns a terminal state; there is no default task deadline. If `--max-poll-ms` is set, leave the task `running` with its original `job_id` and keep that key reserved. A worker becomes idle only after a successful MP4 download and validation or an explicit terminal failure, followed by `client.close()` waiting for all sockets to close. A definite generation or input failure records its reason and releases the worker after shutdown; continue other eligible tasks without silently buying a replacement. Report the product/variant, Key slot, provider code and reason, using “供应商未提供具体失败原因” when absent. Serialize workbook writes after acceptance and settlement.
5. Report downloaded, failed, blocked, submission-unknown, and still-running counts plus the output directory. Include every failed task with product/variant, job ID when present, error code and reason from `task-issues.json` / execution `issues`; distinguish pre-upload image rejections from provider generation failures, and explain pending recovery separately. The workbook task error column must retain the same reason. Never report only failure counts. Run `qa` with explicitly discovered ffprobe/ffmpeg paths to save full-decode checks, dimensions, frame rate, duration, audio-stream checks, frames at least every three seconds including first/last, and a contact sheet. Inspect those images and the audible dialogue; then record the per-task content review using [references/content-qa.md](references/content-qa.md) and rerun `qa --review <content-review.json>`. The file hash must match. Report transport completion separately from `qa_counts` and `qa_complete`; unreviewed content remains pending. Retain failed-QA files and never generate a paid replacement without explicit user authorization.
6. Run `retry-failed --approve <integrity_digest>` only after the user explicitly asks to retry failed items; this creates new paid jobs with new idempotency keys only for definite failures, clears their old credential binding, and returns them to the shared FIFO queue. An uncertain create or a download/protocol failure with an existing job remains pinned to its original key and job.
7. Run `retry-content-failed --approve <integrity_digest>` only after the user explicitly asks to regenerate a downloaded item that has a recorded failed content QA. Preserve the rejected MP4 under a content-addressed `.qa-failed-<hash>.mp4` filename, keep the same validated prompt and reference images, clear its old credential binding, then submit exactly one replacement through the shared FIFO queue with a new idempotency key.

## Command pattern

```powershell
& '<node>' '<skill>/scripts/workflow.mjs' prepare --input '<book.xlsx>' --node-modules '<node_modules>' --python '<python>' --env-file '<workspace>/.env'
& '<node>' '<skill>/scripts/workflow.mjs' validate-prompts --draft '<batch.draft.json>' --prompts '<prompt-batch.json>' --review '<prompt-review.json>'
& '<node>' '<skill>/scripts/workflow.mjs' prepare --input '<book.xlsx>' --draft '<batch.draft.json>' --prompts '<prompt-batch.json>' --review '<prompt-review.json>' --image-review '<image-review.json>' --node-modules '<node_modules>' --python '<python>' --env-file '<workspace>/.env'
& '<node>' '<skill>/scripts/workflow.mjs' execute --manifest '<batch.manifest.json>' --node-modules '<node_modules>' --env-file '<workspace>/.env'
& '<node>' '<skill>/scripts/workflow.mjs' qa --manifest '<batch.manifest.json>' --node-modules '<node_modules>' --ffprobe '<ffprobe>' --ffmpeg '<ffmpeg>'
& '<node>' '<skill>/scripts/workflow.mjs' qa --manifest '<batch.manifest.json>' --node-modules '<node_modules>' --review '<content-review.json>'
```

Use absolute paths. Never log request headers, `.env` contents, signed URLs, or image base64. Treat SQLite as the source of truth and the workbook as its human-readable mirror.

Test-only review fixtures require `--allow-test-review` for local preparation and validation. Such manifests may execute only with `--skip-key-check` and an explicitly loopback HTTP `--base-url`; they cannot authorize production submissions. Never use these flags for real batches.
